# MarketPulse Agent：需求澄清与 MVP 方案收敛

## 1. 阶段目标

在限定时间内定义一个可实现、可演示、可验收的 MarketPulse Agent MVP。用户通过 CLI 输入任意产品方向或关键词，系统自主检索全球英文公开网页，分析市场、竞品与定价信息，最终输出一份带来源引用的中文 Markdown 市场可行性报告。

本文只完成需求澄清和方案收敛，不包含代码、脚手架或实施计划。

## 2. 关键澄清问题与结论

### 问题 1：MVP 的主要交付形态是什么？

**为什么重要：** 交付形态决定系统边界、依赖、演示复杂度与验收方式。Web UI 会引入前端、会话和部署工作，容易稀释对核心 Agent 能力的投入。

**选项：**

- CLI 单次运行，输入关键词后生成 Markdown 报告。
- HTTP API，返回结构化 JSON 或 Markdown。
- 简单 Web 界面。

**结论：** 选择 CLI 单次运行。用户输入关键词及少量可选参数，程序在本地生成 Markdown 文件，并在终端显示执行阶段与最终文件路径。

### 问题 2：首版覆盖哪个市场和语言范围？

**为什么重要：** 市场范围直接影响查询语言、竞品集合、定价币种、数据可比性和最终结论口径。

**选项：**

- 全球市场，以英文公开网页为主，报告用中文输出。
- 中国市场，以中文公开网页为主。
- 全球与中国双市场分别分析。

**结论：** 选择全球市场，以英文公开网页为主要证据来源，统一按来源原币种展示价格，报告使用中文。MVP 不做中国市场的独立分区研究。

### 问题 3：证据来源和可信度标准是什么？

**为什么重要：** 市场报告最常见的失败不是文笔，而是事实不可追溯、价格过期、搜索摘要被误当作原始证据。证据标准会决定检索策略和报告可信度。

**选项：**

- 只追求覆盖面，允许直接使用搜索摘要。
- 关键事实优先引用官方页面，辅以可信第三方来源，并记录访问日期。
- 只允许官方来源，缺失信息一律留空。

**结论：** 采用“官方来源优先、可信第三方补充”的策略。竞品功能与定价优先引用官网、官方定价页或帮助中心；市场趋势可使用研究机构、行业媒体等二级来源。搜索结果摘要只能用于发现页面，不能作为最终证据。每个关键事实都应能映射到 URL，无法验证的内容明确标注“未验证”或“不确定”，不得补写。

### 问题 4：单次运行的时间与成本预算是多少？

**为什么重要：** 没有预算边界的自主 Agent 容易无限扩展查询、重复浏览和产生不可控费用，也难以稳定演示。

**选项：**

- 快速模式：约 1 分钟，少量来源，结论较粗。
- 平衡模式：目标 3–5 分钟，限制搜索与页面抓取数量。
- 深度模式：10 分钟以上，尽量扩大覆盖。

**结论：** MVP 采用平衡模式：目标在正常网络条件下 5 分钟内完成；设置明确的搜索轮次、抓取页面数、重试次数与总超时上限。达到预算后使用已有证据生成报告，并披露覆盖限制，而不是继续无限搜索。

### 问题 5：报告服务于什么决策，必须给出多明确的结论？

**为什么重要：** 如果没有明确决策对象，报告容易退化为资料堆砌，无法体现“市场可行性分析”的价值。

**选项：**

- 只汇总市场与竞品事实，不作判断。
- 面向 SaaS 产品/战略团队，给出 Go、Conditional Go 或 No-Go 建议及置信度。
- 生成完整投资尽调与财务预测。

**结论：** 面向 SaaS 产品负责人和战略团队，给出 **Go / Conditional Go / No-Go** 建议、置信度、判断依据、主要风险和下一步验证动作。MVP 不做投资级尽调、精确市场规模估值或财务模型。

## 3. 可行方案比较

### 方案 A：OpenAI Agents SDK + 显式阶段编排（推荐）

使用一个主 Agent 负责分析与写作，但由代码层按固定阶段控制流程：需求解释 → 搜索规划 → 检索与页面读取 → 证据归一化 → 竞品/定价分析 → 报告生成 → 质量检查。工具调用由 SDK 承载，阶段边界、预算、数据结构和失败策略由程序显式控制。

**优点：**

- 能展示 Agent 工具调用、结构化输出和追踪能力，同时保留可预测的工程边界。
- 各阶段输入输出清晰，容易单元测试、回放和定位故障。
- 后续可自然扩展为并行研究 Agent，但 MVP 不必承担多 Agent 复杂度。

**缺点：**

- 需要理解 SDK 的运行、工具、追踪及结构化输出机制。
- 相比完全自由的 Agent，需要预先定义较清晰的数据契约。

### 方案 B：纯自主 OpenAI Agents SDK Agent

把搜索、浏览、分析和写报告的目标一次性交给 Agent，由模型自行决定工具调用顺序和停止时机。

**优点：** 实现速度快，代码量少，初次演示容易获得“自主 Agent”效果。

**缺点：** 调用次数、延迟和成本不稳定；遗漏定价页或重复检索时难以诊断；报告结构和引用完整度容易漂移。对工程能力与调试思路的展示较弱。

### 方案 C：完全自建确定性工具循环

不依赖 Agents SDK 的编排能力，自行实现状态机、工具调度、重试、上下文管理和终止条件；模型仅用于生成查询、抽取与分析。

**优点：** 控制力最强，行为与预算最可预测，便于针对特定流程优化。

**缺点：** 限定时间内需要编写较多基础设施；容易把时间花在框架代码而非市场研究质量上；可观测性和结构化调用能力需要自行补齐。

### 推荐结论

选择 **方案 A：Agents SDK + 显式阶段编排**。它在开发速度、Agent 自主性、可测试性和调试透明度之间最平衡。模型可以自主生成查询、选择候选页面和形成洞察，但程序必须控制预算、阶段、数据契约和质量门槛。

报告交付采用单个 Markdown 文件；内部阶段使用结构化对象传递数据。MVP 不额外交付 JSON 文件，但保留内部结构化数据，以便测试和未来扩展 API。

## 4. MVP 用户体验

### 输入

必填：

- 产品方向或关键词，例如 `AI meeting notes tools`。

可选：

- 输出文件路径。
- 竞品数量上限，默认 5，允许 3–8。

输入为空、过长或明显无法形成产品方向时，CLI 应立即给出可理解的错误，不发起联网请求。

### 运行过程

终端显示简洁阶段状态，例如：正在规划查询、正在收集来源、正在分析竞品、正在生成报告。默认不输出模型的隐藏推理内容，仅输出阶段、工具结果数量、重试和错误摘要。

### 输出

生成 UTF-8 中文 Markdown 报告，至少包含：

1. 执行摘要。
2. 研究范围、日期与方法说明。
3. 市场信号与需求证据。
4. 3–5 个核心竞品对比表。
5. 定价与商业模式对比。
6. 市场空白、差异化机会与进入壁垒。
7. Go / Conditional Go / No-Go 建议与置信度。
8. 关键风险与下一步验证动作。
9. 来源清单，包含标题、URL、来源类型和访问日期。
10. 局限性与未验证信息。

## 5. MVP 系统边界

### 做什么

- 接受任意英文或中文产品方向/关键词，并将其规范化为全球英文市场研究主题。
- 自动生成一组有差异的英文搜索查询，覆盖市场需求、核心竞品、官方功能页和官方定价页。
- 联网搜索并读取公开可访问网页。
- 去重、筛选并保存结构化证据，包括来源 URL、页面标题、访问日期、证据类型和支持的事实。
- 分析 3–5 个最相关竞品，比较定位、主要功能、目标客户、免费层/试用及公开价格。
- 对关键结论附可点击引用；事实与推断在表达上明确区分。
- 在搜索失败、页面打不开或信息冲突时降级运行，并在报告中披露。
- 输出结构稳定的中文 Markdown 市场可行性报告。
- 记录足够的运行日志与阶段指标，支持复现和调试。

### 不做什么

- 不构建 Web UI、HTTP 服务、账户系统、数据库或云端部署。
- 不做长期会话、定时监控、历史报告管理或增量更新。
- 不登录网站，不绕过付费墙、验证码、robots 限制或反爬机制。
- 不抓取社交平台私有数据、用户评论全量数据或需要授权的数据源。
- 不承诺精确 TAM/SAM/SOM 数值；没有可靠来源时只给出定性市场信号。
- 不做完整财务模型、投资回报预测、法律合规审查或替代人工尽调。
- 不做多 Agent 并行研究、向量数据库、RAG 知识库或复杂记忆系统。
- 不自动生成幻灯片、PDF、Excel 或 JSON 交付物。
- 不自动安装浏览器、购买搜索服务或要求多个外部 API 密钥。

## 6. 建议的逻辑组件与边界

本节定义组件职责，不等同于实施计划。

1. **CLI 入口**：解析关键词和选项，校验输入，创建本次运行上下文。
2. **研究规划器**：把主题转为研究维度与有限数量的英文查询；不负责访问网页。
3. **搜索工具适配器**：执行搜索，返回规范化候选结果；隐藏具体搜索供应商差异。
4. **页面读取器**：抓取公开页面并提取正文；负责超时、内容类型和大小限制。
5. **证据仓库（运行时内存）**：去重并保存来源、事实、时间戳与可信度标签；不做持久化数据库。
6. **市场分析器**：基于证据生成市场信号、竞品矩阵、定价比较、机会与风险；不得引入无来源事实。
7. **报告生成器**：将结构化分析渲染为固定章节的中文 Markdown。
8. **质量门禁**：检查必要章节、引用完整度、竞品数量、未验证标记及最终建议是否存在。
9. **运行追踪与日志**：记录各阶段耗时、查询数、页面成功/失败数、重试与 token/调用量（若 SDK 可提供）。

这些组件通过明确的结构化数据契约连接，以便单独测试和替换。搜索供应商、模型或页面提取实现发生变化时，不应影响报告模板和 CLI 接口。

## 7. 核心数据流

1. CLI 校验用户输入并建立运行预算。
2. 研究规划器生成研究问题与查询集合。
3. 搜索工具返回候选 URL，系统按域名、相关性和来源类型去重排序。
4. 页面读取器抓取优先级最高的页面；失败时在预算内重试或选择候补来源。
5. 抽取结果进入证据仓库，事实绑定具体来源，不保留无法定位来源的关键断言。
6. 若竞品、官方定价或市场证据覆盖不足，系统在剩余预算内执行一次定向补搜。
7. 市场分析器只基于证据仓库生成结构化判断。
8. 报告生成器输出 Markdown，质量门禁执行最终检查。
9. 若非致命检查失败，报告仍可生成，但必须在开头或局限性章节显著披露；致命失败则返回非零退出码。

## 8. 错误处理与降级原则

- **搜索服务不可用：** 有限次数指数退避；仍失败则终止并返回非零退出码，不生成伪报告。
- **单页抓取失败：** 记录原因并尝试候补来源，不阻塞整个任务。
- **动态页面或正文为空：** 标记不可读取；MVP 不引入浏览器自动化作为默认兜底。
- **定价信息缺失：** 明确写“未公开/未验证”，不得推测价格。
- **来源相互冲突：** 优先官方且更新日期较新的来源，同时在报告中披露冲突。
- **达到时间或调用预算：** 停止扩展搜索，使用已有证据生成带覆盖限制的报告。
- **模型输出结构不合法：** 在同一阶段进行有限次数修复；超过次数则记录失败并终止或降级。
- **写文件失败：** 保留错误信息并返回非零退出码；不声称报告已生成。

## 9. 调试与可观测性要求

为体现工程能力，MVP 的调试设计必须能够回答“失败发生在哪一阶段、用过哪些来源、为何得出此结论”：

- 每次运行生成唯一运行 ID。
- 记录阶段开始/结束时间、耗时和结果计数。
- 记录搜索查询、候选 URL、抓取状态、重试次数和舍弃原因。
- 保存来源到证据的映射，便于发现“有引用但不支持结论”的问题。
- 区分工具错误、网络错误、结构化输出错误、质量门禁失败和预算终止。
- 日志不得包含 API Key、完整环境变量或模型隐藏推理。
- 支持用固定的工具响应样本离线复现分析与报告阶段，降低调试对网络的依赖。

## 10. 验收标准

### 功能验收

- 执行一条 CLI 命令并输入 `AI meeting notes tools`，可在正常网络条件下生成一个可打开的 UTF-8 中文 Markdown 文件。
- 报告包含约定的 10 个章节，且章节顺序稳定。
- 报告比较 3–5 个真实、相关的全球竞品。
- 每个竞品至少包含官网或官方产品页来源；公开定价存在时，价格字段必须引用官方定价页。
- 报告包含明确的 Go / Conditional Go / No-Go 结论、置信度、至少 3 条依据、主要风险与下一步验证动作。

### 证据质量验收

- 报告至少包含 8 个去重后的可点击来源，其中至少 3 个为竞品官方页面。
- 关键市场事实、竞品能力和价格信息均可追溯到具体 URL；抽样点击链接可访问且与断言相关。
- 搜索摘要不作为最终引用来源。
- 无可靠证据的信息被标记为未验证或局限性，不出现明显编造的价格、市场规模或客户数据。
- 报告显示研究日期，并区分事实、分析推断和建议。

### 稳定性与工程验收

- 单个页面失败不会导致整次运行崩溃；报告会披露缺失信息。
- 搜索服务整体不可用、输出文件不可写等致命错误会返回非零退出码和可操作的错误信息。
- 正常网络条件下目标完成时间不超过 5 分钟；无论成功与否，都受总超时和调用预算约束。
- 相同固定工具响应输入下，报告结构和竞品数据字段可重复验证。
- 日志可定位各阶段耗时、工具调用数、页面成功/失败数及最终质量检查结果，且不泄露密钥。

### 测试用主题

至少使用以下三类主题验证通用性：

- `AI meeting notes tools`：成熟且竞品丰富的 SaaS 类别。
- `AI contract review for small businesses`：垂直专业场景。
- `carbon accounting software for SMBs`：非纯 AI、价格信息可能不完整的场景。

三次运行都应保持相同报告结构；允许证据数量和结论不同。

## 11. MVP 成功定义

MVP 的成功不是“搜索到尽可能多的网页”，而是：在受控时间与调用预算内，针对不同产品方向稳定生成一份结构清晰、关键事实可追溯、局限性透明、能够支持下一步市场决策的中文报告；同时，工程人员可以通过日志和阶段数据快速解释与复现失败。

## 12. 已知风险与后续阶段待验证项

- 搜索工具或供应商在目标运行环境中的可用性、速率限制和成本需要在技术方案阶段验证。
- 部分 SaaS 定价页依赖 JavaScript，纯 HTTP 抓取可能无法读取；MVP 优先使用可访问的官方替代页面，并披露缺失。
- “市场规模”类数据经常付费或口径不一致，因此首版以需求信号和竞品密度为主，不强制输出精确数值。
- LLM 生成的分析仍可能超出证据范围，必须依赖证据映射和最终质量门禁约束。
- 当前文档只批准需求与设计边界；开始实施前仍需单独产出并确认实施计划。
